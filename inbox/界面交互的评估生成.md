# 交互数据的分析重用：研究思路分享

> **一句话主张**：从今天的任务链路和真实页面中提取任务约束与设计判断，让未来可塑界面能针对个体化、一次性需求可靠地重新组织——不假定未来界面模仿今天的界面。

---

## 问题：现有界面数据能为可塑界面提供什么

可塑界面（Malleable Interface）的生成，当前有两条已发表的路线，但都**没有回答"现有界面数据能贡献什么"**：

1. **Jelly（CHI 2025）为代表的路线，直接使用 LLM**：LLM 从一句任务描述生成对象-关系模型、依赖图、界面规范。它的"设计知识"来自模型预训练吸收的通用常识，不需要扫描任何现有界面数据。
2. **Malleable Overview-Detail（CHI 2025）分析了 303 个真实界面实例**，但目的是建立"内容/组合/布局"三维**设计空间**，据此设计定制技术——不是提取可复用的设计经验数据集。

由此留下一个开放问题：**显式任务/界面数据，能否补充 LLM 内化知识之外的某些东西？**

LLM 有三个已知边界，显式数据可能恰好补这三处：

| LLM 内化知识的边界 | 显式任务/界面数据可能提供的 |
|---|---|
| 知道"平均上"怎么做，但不知道特定领域/平台/时期的具体惯例 | 该平台/品类真实的约束与惯例（如电商履约链路、医疗界面的安全要求） |
| 无法溯源：为什么这样设计？依据是什么？ | 每条设计判断可追溯到真实实例，可审计、可校正 |
| 对长尾/低频场景覆盖弱（训练语料里少见） | 真实长尾任务的执行样本，即使少量也有锚定价值 |

---

## 主张：提取三类结果

现有界面沉淀了真实任务的执行方式，以及人的信息处理和操作边界。

- **通用结构**——反复出现的任务单元与设计模式；
- **必要约束**——不能破坏的安全、权责、恢复要求；
- **可变化部分**——可随情境省略、替换或重组的内容。

```
任务链路（事情怎样做完） + 真实页面（设计师怎样安排信息和操作）
        ↓ 提取
通用结构 / 必要约束 / 可变化部分
        ↓ 用于
未来界面：面向个体、一次性需求，继承约束，重组流程、信息和操作
```

---

## 路径：任务层与界面层的两层提取

### 任务层：从链路中提取任务执行知识

| 任务知识   | 核心问题                    | 典型内容              |
| ------ | ----------------------- | ----------------- |
| **信息** | 当前阶段必须知道什么？什么可以延后？      | 价格、时间、状态、来源、约束    |
| **行动** | 需要做什么？哪些动作有先后或依赖？       | 搜索、筛选、比较、选择、确认、提交 |
| **权责** | 谁可以发起、修改和确认？系统能代做到什么程度？ | 用户确认、平台校验、第三方履约   |
| **安全** | 什么情况下必须提醒、确认或增加摩擦？      | 高金额、不可逆操作、敏感权限    |
| **恢复** | 失败或后悔后怎样回到可控状态？         | 返回、撤销、修改、重试、取消、退款 |

### 界面层：从页面中提取设计判断

"重要信息更显著、高频操作更易触达"这类原则太浅，基础模型也能推理。值得提取的是它们的**条件与边界**：

| 条件 | 常见设计选择 | 需要数据回答的问题 |
|---|---|---|
| 高频且当前任务相关 | 更显著、更靠前、更易触达 | 显著到什么程度？何时需要常驻？ |
| 低频但高风险 | 入口不必突出，但增加确认和摩擦 | 什么条件下需要二次确认？ |
| 信息多、目标明确 | 突出关键字段，延后次要信息 | 第一层必须保留哪些信息？ |
| 需要比较候选 | 并列关键属性，弱化无关内容 | 哪些属性应升为一级信息？ |
| 已有可信信息 | 减少重复输入，压缩步骤 | 哪些可以默认，哪些仍要确认？ |

> ⚠️ **真实界面不是天然正确的**：显著性既可能服务用户任务，也可能服务平台商业目标。若做数据驱动，需先区分"设计意图"与"商业意图"，否则学到的是平台利益而非用户价值。

### 与 Malleable O-D 的界线

O-D 是本提案最接近的已有工作，但止步于设计空间：

- **它做了**：分析 303 个真实概览-详情实例 → 归纳出三维设计空间 → 设计 Fluid Attributes 定制技术。
- **它没做**：没有把"某条件下某设计选择更常见/更有效"沉淀为可重用的判断规则；其知识体现在技术设计里，而非可查询的数据集中。

本提案在 O-D 的基础上，把产出从"设计空间"推进到"条件-决策规则"。

## 依据：跨任务聚合能否发现稳定规律

单个任务只有少量同类样本不是致命问题——只要不同任务反复使用相同的**任务单元**和**设计判断**，就可以跨任务聚合，判断规律是否稳定、何时失效。

| 少量同类样本 | 大规模跨任务数据 |
|---|---|
| 知道某个任务通常怎么做 | 知道哪些任务结构跨领域反复出现 |
| 知道某个页面通常怎么设计 | 知道同一条件是否稳定对应相似设计选择 |
| 得到几个设计模式 | 得到规律的适用范围、边界和例外 |
| 为已知任务找参考 | 为未见任务提供可组合的任务与设计先验 |

**这是本提案的核心假设**："同条件 → 同设计选择"的对应在真实数据中是否足够稳定、是否超越 LLM 内化知识，需要靠验证环节回答。若 R1（见下）显示跨平台一致性很低，数据只会引入噪声，这条路就不成立。

## 示例：电商任务的约束继承

需求："买一台 3000 元以内、明天能到、续航好的平板。"

| 阶段        | 任务知识                   | 现有设计经验                   | 未来界面                  |
| --------- | ---------------------- | ------------------------ | --------------------- |
| **候选与比较** | 价格、品类、配送、续航、评价等条件与可比信息 | 搜索/筛选高可达，关键属性并列，次要营销信息弱化 | 直接形成短名单，并突出续航、价格和到货时间 |
| **配置**    | 确认型号、容量、数量等影响商品身份的信息   | 高影响选项显式，低风险默认值可减少操作      | 只保留相关规格，并提示其对价格和配送的影响 |
| **提交**    | 必须明确商品、金额、地址、配送和支付     | 高承诺操作前重新突出关键信息并保留确认      | 前面可以压缩，但付款前完整核验关键交易信息 |
| **恢复**    | 支持修改、取消、退款和重试          | 错误状态可见，恢复入口可达            | 简化界面也不能删除恢复路径         |

这个例子演示"必要约束"（付款前核验、保留恢复路径）如何被继承。这些约束在 LLM 内化知识里可能部分存在，但"具体到某个平台的履约链路"是领域特有数据才有的——这是"数据 vs LLM"差异的一个具体实例。

## 验证：数据相对 LLM 内化知识的增量

路线是否有价值，取决于一个可检验的问题：**显式任务/界面数据能否提供 LLM 内化知识之外的经验？**

> 对照实验：让强基础模型只根据任务描述，预测页面的信息显著性、操作优先级和安全安排；再比较加入真实任务与界面数据后，对未见 App、未见任务的预测是否明显提升。

### 三种可能结果与后续取向

| 结果 | 结论 |
|---|---|
| 提升主要出现在条件、边界和例外上 | 数据提供了可迁移的设计经验，支持继续建设数据 |
| 基础模型本身已能稳定预测 | LLM 内化知识足够，需重新评估继续扩充数据的价值，或转向"数据用于审计/溯源"而非"数据用于生成" |
| 提升集中在安全/权责等领域必要约束上 | 数据价值在领域约束而非通用设计，应聚焦垂直领域数据 |

### 研究问题

1. **R1（一致性）**：同一条件下，跨页面、跨平台的设计选择一致性有多高？一致则存在可学习规律；不一致则数据会引入噪声。
2. **R2（增量性）**：相对纯 LLM 基线，加入数据后对未见任务的预测提升多大？提升来自哪些层面？
3. **R3（边界性）**：数据帮助的是通用设计常识，还是领域必要约束？二者各占多少？
4. **R4（机制性）**：如果数据有用，是因为提供了 LLM 不知道的事实，还是提供了可溯源的证据使 LLM 输出可被校正？

## 定位：Abstraction Spaces 中的经验密度

Abstraction Spaces（Min, Suh, Hollan & Xia, 2026）把交互摩擦刻画为用户心智抽象与系统抽象之间的"抽象鸿沟"（超调/欠调），并把抽象描述为**空间**而非梯子。本提案可在这套理论中定位：

- 现有界面的任务链路与页面，是"设计师如何对任务做抽象"的沉淀（每个页面 = 抽象空间中的一个点）；
- 大规模跨任务数据的目标，是测量这些点如何聚集——哪些抽象反复出现（通用结构）、哪些不可动摇（必要约束）、哪些随情境移动（可变化部分）；
- 未来可塑界面的"继承约束 + 重组信息"，等价于在抽象空间中沿合法轨迹移动，而非从零选点。

用真实界面数据为"抽象空间"补充经验密度，为可塑界面提供可参考的设计落点。

![[inbox/assets/malleable-interface-sharing/abstraction-spaces.png]]

*图 2　Abstraction Spaces 在经典执行/评估鸿沟之外，显式加入用户心智抽象与系统抽象之间的"抽象鸿沟"。来源：Making Abstraction Concrete：Design Space and Interaction Model of Abstraction，原论文 Fig. 1。*
